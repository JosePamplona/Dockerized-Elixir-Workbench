# clustering — Design

*Revision: cartridge v0.2.0 (2026-08-30). Sources consulted on that
date; quotations are verbatim from the file or page as read then. The
mechanism as installed is in the [README](README.md); this paper holds
the alternatives and the evidence.*

## Abstract

A `phx.new` project already contains cluster discovery: the
`dns_cluster` dependency, a `DNSCluster` child in the supervision tree,
and a `DNS_CLUSTER_QUERY` read in `config/runtime.exs`. What it lacks
is a release that boots as a *named* distributed node — without one,
`DNSCluster` has nothing to dial and says so at boot. The cartridge
adds no dependency and no Elixir: it appends a six-line POSIX `sh`
block to `rel/env.sh.eex` that names the node after the container's
address at boot, writes the other three `mix release.init` templates
from Mix's own functions, and declares the query in `.env`. The
alternatives — libcluster's strategies, static node names, putting the
release variables in `.env`, `vm.args` or the Dockerfile, copying the
templates into this repository — were rejected on what the sources do
with each. Because a workspace runs one `app` container inside a shared
network namespace, the cartridge cannot be seen working there; the
workbench's `up --deploy scaled` deployment, a different compose
topology, is where it was verified: four replicas on a bridge network
behind nginx, one address each, one DNS name answering with all four.

## 1. Problem

Distributed Erlang needs three things to agree: every node must have a
name of the form `basename@host` that the others can reach, every node
must share a cookie, and something must tell each node the names of the
others. `phx.new` settles the third with `DNSCluster` and leaves the
first untouched — Mix's release script defaults to a *short* name
(`RELEASE_DISTRIBUTION=sname`, §2.3), which cannot carry an IP address,
and `DNSCluster` requires long names (§2.2). The question for the
workbench was where the smallest possible fix belongs, so that a
project keeps everything `phx.new` gave it, gains nothing it does not
need, and the fix survives the workbench's own regeneration of the
workspace files. A second question followed from the first: a
workspace has nothing to cluster *with* (§2.5), so where can the result
be seen?

## 2. Background

### 2.1 What `phx.new` leaves in the tree

Read in the `test_28` workspace (`lorem_ipsum_8`, Phoenix 1.8 as
generated by the workbench's toolchain) [1]:

* `mix.exs`: `{:dns_cluster, "~> 0.2.0"}`; the lock resolves it to
  `0.2.0`.
* `lib/lorem_ipsum_8/application.ex`, in the supervisor's children:
  `{DNSCluster, query: Application.get_env(:lorem_ipsum_8, :dns_cluster_query) || :ignore}`.
* `config/runtime.exs`, inside `if config_env() == :prod do`:
  `config :lorem_ipsum_8, :dns_cluster_query, System.get_env("DNS_CLUSTER_QUERY")`.

So in `dev` and `test` the child starts with `query: :ignore` whatever
the environment holds, and in `prod` an unset variable yields `nil`,
which `|| :ignore` turns into the same. The variable is inert unless
the release runs.

### 2.2 What `DNSCluster` 0.2.0 does

Read in full: `deps/dns_cluster/lib/dns_cluster.ex` [2].

* `init/1`: `query: :ignore` returns `:ignore` (the child is not
  started); otherwise it calls `warn_on_invalid_dist/0` and keeps the
  *basename of the current node* — `resolver.basename(node())`, the
  part before `@` — as the basename it will dial.
* Every `interval` (default `5_000` ms) it resolves each query for `:a`
  and `:aaaa` records through `:inet_res.getbyname/2`, builds
  `"#{basename}@#{ip}"` for every address, drops the ones already in
  `Node.list(:visible)`, and calls `Node.connect/1` on the rest
  concurrently (`connect_timeout` default `10_000` ms).
* `lookup/2` maps `{:error, _}` to `[]`: an unresolvable query is not
  an error, it is an empty peer list. `log` defaults to `false`, so
  a successful connection logs nothing either.
* `warn_on_invalid_dist/0` reads `:net_kernel.get_state/0`. With
  `RELEASE_NAME` set (i.e. inside a release) and distribution not
  started it logs:

  > node not running in distributed mode. Ensure the following exports
  > are set in your rel/env.sh.eex file:
  >
  >     #!/bin/sh
  >
  >     export RELEASE_DISTRIBUTION=name
  >     export RELEASE_NODE="myapp@fully-qualified-host-or-ip"

  and with distribution started under *short* names:

  > node not running with longnames which are required for DNS
  > discovery.

The moduledoc's own rule: "Nodes will only be joined if their node
basename matches the basename of the current node" [2]. The basename
is therefore fixed by whoever names the node; `DNSCluster` cannot be
told a different local one, only remote ones (`{basename, query}`).

### 2.3 What the release boot script does with `env.sh`

Read in full: `Mix.Tasks.Release.Init` (Elixir 1.19.5) [3], which
holds the text of every default template, and the relevant parts of
`Mix.Tasks.Release` [4].

The `bin/<app>` script is `cli_text/0`. It begins `#!/bin/sh`, exports
`RELEASE_NAME` (defaulting to the release name baked in), sources the
environment file — `. "$REL_VSN_DIR/env.sh"` — and *only then* applies
the defaults:

```sh
RELEASE_COOKIE="${RELEASE_COOKIE:-"$(cat "$RELEASE_ROOT/releases/COOKIE")"}"
RELEASE_NODE="${RELEASE_NODE:-"$RELEASE_NAME"}"
RELEASE_DISTRIBUTION="${RELEASE_DISTRIBUTION:-"sname"}"
```

`start` then runs `elixir --cookie "$RELEASE_COOKIE"
--$RELEASE_DISTRIBUTION "$RELEASE_NODE" …`; `remote` opens a hidden
node named `rem-<random>-$RELEASE_NODE` with `--remsh "$RELEASE_NODE"`,
so it goes through the same `env.sh` and reaches the node the script
named. Three consequences the cartridge relies on:

1. `$RELEASE_NAME` is available inside `env.sh`, and it is the string
   the release's `node()` will begin with.
2. Anything `env.sh` exports wins over the defaults; anything it
   leaves unset gets them. Conversely, a variable set *before* the
   script runs is visible to `env.sh` too.
3. The script is `sh`, and it sources `env.sh` with `.` — the
   environment file runs under whatever `/bin/sh` is, never under bash,
   regardless of what the image ships.

`rel/env.sh.eex` is an EEx template rendered at `mix release` into
`releases/<vsn>/env.sh` (`cli_for(:unix, …)` in [4]); the same is true
of `vm.args.eex`, `remote.vm.args.eex` and `env.bat.eex`, and *each
one independently* falls back to the built-in default when the `rel/`
file is absent (`make_vm_args/2` and `copy({:executables, …})` both
test `File.exists?` per template) [4]. Mix's documentation of the
variables [4]:

> `RELEASE_DISTRIBUTION` - how do we want to run the distribution.
> May be `name` (long names), `sname` (short names) or `none`
> (distribution is not started automatically). Defaults to `sname`.
> When connecting nodes across hosts, you typically want to set this
> to `name` (required to use IPs as host names)

and of the cookie:

> If this option is not set, a random cookie is written to the
> `releases/COOKIE` file when the first release is assembled. At
> runtime, we will first attempt to fetch the cookie from the
> `RELEASE_COOKIE` environment variable and then we'll read the
> `releases/COOKIE` file.

The assembly step that writes it is `Mix.Release.make_cookie/2` [4].

### 2.4 What `mix release.init` writes

`run/1` creates four files from four public functions marked
`@doc false`: `vm_args_text(false)`, `vm_args_text(true)`,
`env_text()`, `env_bat_text()` [3]. The default `env.sh.eex` carries
the distributed pair *commented out*:

```sh
# # Set the release to work across nodes.
# # RELEASE_DISTRIBUTION must be "sname" (local), "name" (distributed) or "none".
# export RELEASE_DISTRIBUTION=name
# export RELEASE_NODE=<%= @release.name %>
```

and the default `vm.args.eex` opens with "`-mode/-name/-sname/-setcookie`
are configured via env vars, do not set them here" [3].

### 2.5 What the workbench's two composes do with the network

`scripts/docker-compose.seed.yml` [5], baked into every workspace's
`docker-compose.yml` and `docker-compose.prod.yml`: a `network` service
(`registry.k8s.io/pause:3.10`) owns the published ports, and `app`,
`database` and `pgadmin` join it with `network_mode: "service:network"`
— "Pod pattern", so that all of them reach each other on `localhost`
and the project keeps Phoenix's default database configuration. The
Compose specification: `network_mode: "service:{name}"` "gives the
container access to the specified container by referring to its
service name", and "When set, the `networks` attribute is not allowed"
[6]. The README records the measurement that settles what scaling such
a service does: two `alpine` replicas behind a `pause` container got
the same IP and the same hostname, and the second died on the port
bind.

`scripts/docker-compose.scaled.seed.yml` [7] is a different file, not a
variant: the replicas are plain services on the project's default
bridge network, each with `networks.default.aliases: [app]`, an
`environment` block that overrides two entries of the shared `.env`
(`DNS_CLUSTER_QUERY: app`, `DATABASE_URL: …@database/…`), a `migrate`
one-shot the replicas `depends_on` with
`condition: service_completed_successfully`, an optional nginx
`balancer` whose config adds `X-Served-By $upstream_addr`, and a
`database` created from `POSTGRES_DB`. `bake_scaled_compose` in
`wb.sh` [8] expands `%{app_services}`, `%{balancer_depends}` and
`%{upstream_servers}` into `app1..appN` (`--replicas`, default 4),
gives each a host port from the first free one after the balancer's,
deletes the balancer and its config under `--no-balancer`, deletes the
`DNS_CLUSTER_QUERY:` line when `clustering_installed` — a `grep` for
`Workbench clustering:` in `rel/env.sh.eex` — fails, and drops
`migrate`, `database` and `DATABASE_URL` when the project has no
database. `up --deploy scaled` bakes, then runs `docker compose up
--detach --build --remove-orphans` on the file.

On the Compose side of aliases: "a network-wide alias can be shared by
multiple containers, and even by multiple services. If it is, then
exactly which container the name resolves to is not guaranteed" [6];
the embedded DNS server that answers is at `127.0.0.11` on every
user-defined network [9]. The README's `nslookup app` shows what that
non-guarantee looks like on the wire — three A records — and that
`getent hosts app` returns one of them.

### 2.6 What `:inet_res` is

Erlang's own resolver: "A rudimentary DNS client" that "performs DNS
name resolving towards recursive name servers"; `getbyname/2` is
`getbyname(Name, Type, [], infinity)` and returns a `#hostent{}` with
the full `h_addr_list` for `a` and `aaaa` [10]. It is not the C
library's `getaddrinfo`; it does not go through NSS, `/etc/hosts`, or
whatever address-selection the libc applies. `DNSCluster` uses nothing
else (§2.2).

### 2.7 What the two setup lines and the entrypoint do

`scripts/entrypoint.sh` [11]: the opinionated line (`workbench_setup`)
ends with `mix phx.gen.release --docker && mix release.init`; the
vanilla line (`workbench_setup2`) ends with `mix phx.gen.release
--docker` alone, with the comment that `release.init`'s four templates
"are pure customization scaffolding (Mix carries the same defaults
built in) and belong to the clustering cartridge, which writes them
with the exports a distributed release actually needs". The `.env`
template both lines render (`priv/setup/templates/env.eex` [12])
carries no cluster variable; the README of a project generated by the
opinionated line (`priv/setup/templates/readme.eex`) still documents
`DNS_CLUSTER_QUERY`, `RELEASE_DISTRIBUTION` and `RELEASE_NODE` in its
variables table.

### 2.8 What other platforms put in the same two places

Phoenix's deployment guide names the same file and the same pair, with
the node's address coming from the platform: `RELEASE_DISTRIBUTION="name"`,
`RELEASE_NODE="app-${PLATFORM_DEPLOYMENT_SHA}@${PLATFORM_DEPLOYMENT_IP}"`,
and `DNS_CLUSTER_QUERY` as "a DNS query which will be used to find the
IPs of the other instances" [13]. Fly.io's Elixir guide:
`RELEASE_NODE="${FLY_APP_NAME}-${FLY_IMAGE_REF##*-}@${FLY_PRIVATE_IP}"`
with `DNS_CLUSTER_QUERY="${FLY_APP_NAME}.internal"` [14], a name whose
"AAAA record will contain all the 6PN addresses of the started Fly
Machines that belong to the … Fly App" [15]. Kubernetes: a headless
Service's `my-svc.my-namespace.svc.cluster-domain.example` "resolves to
the set of IPs of all of the Pods selected by the Service", where a
normal Service's resolves to one cluster IP [16].

### 2.9 What libcluster offers

libcluster 3.5.0 [17] ships `Epmd`, `LocalEpmd`, `ErlangHosts`,
`Gossip` ("uses multicast UDP to form a cluster between nodes gossiping
a heartbeat"), `Kubernetes` ("uses the Kubernetes Metadata API to query
nodes based on a label selector and basename"), `Kubernetes.DNS` ("uses
DNS to join nodes under a shared headless service in a given
namespace") [17, 19], `Rancher`, and `DNSPoll`, which "Assumes you have
nodes that respond to the specified DNS query (A record), and which
follow the node name pattern of `<name>@<ip-address>`", polling every
`5_000` ms by default with a required `query` and `node_basename` [18].

## 3. Design

### 3.1 Discovery: keep `DNSCluster`; add nothing

Three ways to have the replicas find each other:

1. **libcluster.** `DNSPoll` and `Kubernetes.DNS` are the mechanism
   `DNSCluster` already implements — a DNS name that answers with
   every peer's address, dialled as `<basename>@<ip>` (§2.9 against
   §2.2), with the same default interval. Choosing them would add a
   dependency, a `:libcluster` topology in config, and a second child
   beside the one `phx.new` put in the tree, for the same DNS query.
   `Gossip` needs multicast UDP, which neither of the two networks the
   cartridge's defaults point at (a Kubernetes cluster, Fly's
   `.internal`) offers to an application; `Kubernetes` needs the API
   and a service account. Rejected for the cartridge — and not
   *excluded*: libcluster "plugs into the same supervision tree and
   does not conflict" (README, *Related*), because the cartridge
   touches nothing in the tree.
2. **Static names.** `RELEASE_NODE=app@app1` per replica, and a list of
   peers for `net_kernel` to connect at boot. Every replica of the
   scaled compose shares one `x-app` anchor and one `.env` (§2.5), so
   the name would have to come from somewhere per-container anyway —
   and the peer list would tie the release to the replica count the
   compose happened to be baked with. Short names (`--sname`) fail
   outright: `DNSCluster` warns that long names are required (§2.2).
3. **`DNSCluster` as generated, with a named node.** Chosen. The
   cartridge's whole footprint is the boot script's export pair and
   one environment variable; the discovery loop, its interval, its
   silence on an empty answer, are `phx.new`'s. The basename rule of
   §2.2 dictates the one line that matters: the node must be
   `$RELEASE_NAME@<ip>`, because `$RELEASE_NAME` is what `node()`'s
   basename will be, and every peer dials that basename at every
   address the query returns.

What is given up: any discovery that is not DNS. That is what the
README's *Related* points to.

### 3.2 The release pair lives in `rel/env.sh.eex`

`RELEASE_DISTRIBUTION=name` and `RELEASE_NODE=<name>@<ip>` could sit in
four places. The README's *Variable ownership* section states the
outcome; this is the comparison.

* **`.env`.** Where the workbench parks configuration, and where the
  three variables sat commented out in the `workbench.setup` template
  before the cartridge existed. Compose passes an `env_file` as static
  text: no container knows its address before it runs, and all four
  replicas read the same file (§2.5), so a `RELEASE_NODE` there is the
  same string in four containers — the duplicate name the scaled seed's
  header warns about. `DNS_CLUSTER_QUERY` *does* belong there: it is
  the same for every replica and inert outside `:prod` (§2.1).
* **`rel/vm.args.eex`.** The file for VM flags — and its own first
  lines say "`-mode/-name/-sname/-setcookie` are configured via env
  vars, do not set them here" (§2.4). An EEx template rendered at
  `mix release` time cannot compute a runtime address either.
* **The Dockerfile.** `ENV` is static too, and the file is Phoenix's
  (`mix phx.gen.release --docker`, §2.7), regenerated from the
  toolchain's versions rather than owned by a cartridge.
* **`rel/env.sh.eex`.** Chosen. It is the one file the release runs
  *on every command* (§2.3, [4]) before applying its defaults, so it
  can read `$RELEASE_NAME`, ask the container for its address, and
  export the pair; it is the file `DNSCluster`'s own warning names
  (§2.2); it is where Phoenix's guide and Fly.io's put the same two
  lines (§2.8). The block:

  ```sh
  # Workbench clustering: boot as a named distributed node.
  if [ -z "$RELEASE_NODE" ]; then
    RELEASE_NODE_IP="$(hostname -i 2>/dev/null)"
    RELEASE_NODE_IP="${RELEASE_NODE_IP%% *}"
    export RELEASE_NODE="$RELEASE_NAME@${RELEASE_NODE_IP:-127.0.0.1}"
  fi
  export RELEASE_DISTRIBUTION=name
  ```

  Each line against the sources. `-z "$RELEASE_NODE"`: a name set
  before the script runs — a platform's, as in §2.8 — is visible here
  and is kept. `hostname -i`, first word: a container on several
  networks answers with several addresses, and one must be picked
  consistently. `$RELEASE_NAME@`: the basename rule (§3.1).
  `:-127.0.0.1`: a container with no resolvable hostname still boots,
  as a node nobody can reach, which is the pre-cartridge state, not a
  crash. POSIX `sh`: the script that sources this file is `#!/bin/sh`
  (§2.3, point 3) — the README gives "the production runner image has
  no bash" as the reason, and the runner (`debian:*-slim`) does have
  bash, which the compose healthcheck relies on; the constraint is the
  interpreter, and it holds whether or not bash is installed.

  *What the cartridge does not do:* it does not touch
  `RELEASE_COOKIE`. §3.5.

### 3.3 The other three templates: Mix's functions, not copies

Once the cartridge writes `rel/env.sh.eex`, the question was what to do
about `vm.args.eex`, `remote.vm.args.eex` and `env.bat.eex`. Mix does
*not* require them — each template falls back on its own (§2.3) — so
the reason to write them is a different one: the vanilla setup line
skips `mix release.init` and hands the whole job to this cartridge
(§2.7). Writing the four makes a project on either line carry the same
`rel/`, and makes the cartridge the `release.init` of the vanilla line
plus one block, rather than a fifth file beside three missing ones. (The
README says the three "have to exist alongside `env.sh.eex`"; they do
not have to, and that sentence is listed in §5.)

Three ways to produce their text:

1. **Copy the templates into `priv/features/clustering/`**, like every
   other cartridge's assets. They would be a snapshot of one Elixir
   version's defaults; a project generated by a later toolchain would
   get an older `vm.args` than `mix release.init` would give it, and
   nobody would notice until it mattered.
2. **Compose `mix release.init`** with `Igniter.compose_task/3`. It
   uses `Mix.Generator.create_file/3`, which writes to disk at once,
   outside the patch set: the files would not show in the diff, and
   in the test project (in-memory) they would land on the real
   filesystem.
3. **Call the functions that hold the text** — `vm_args_text/1`,
   `env_bat_text/0`, `env_text/0` (§2.4) — and put the result through
   `Igniter.create_new_file/4` with `on_exists: :skip`. Chosen: the
   text is the running Elixir's, exactly what `release.init` would
   write at that version, and it is in the patch set. The cost is that
   the functions are `@doc false`: public, but not a contract.
   `release_init_texts/0` therefore checks `function_exported?/3` for
   each and, when a future Elixir drops one, the cartridge **queues**
   `mix release.init` with `Igniter.add_task/3` — a shell command run
   after the patch set is applied, so the files appear on disk rather
   than in the diff — and says so in a notice. (Queued, not composed:
   composing would have the write-to-disk problem of option 2 in the
   very run whose diff is being shown.)

`env.sh.eex` is the one file with two paths: created from `env_text/0`
plus the block when absent, or the existing file — the opinionated
line's `release.init` leaves one behind, and so may a developer —
included and appended to (§3.6). The test suite pins option 3 to the
running Elixir: three of the four files are asserted *equal* to the
functions' output, `env.sh.eex` to contain it.

### 3.4 The scaled topology: leave the pod, share an alias

A workspace's compose cannot show clustering (§2.5, §3.5). The choices
for where it *can* be shown:

1. **`docker compose up --scale app=N` on the workspace compose.**
   Measured and rejected (README, *Why a workspace cannot cluster with
   itself*): replicas in `network_mode: "service:network"` share the
   namespace, so they share the address and the port. One binds, the
   rest die, and every `RELEASE_NODE` computed from `hostname -i` is
   the same name.
2. **A flag on the same seed** that swaps the pod for a bridge when
   set. Rejected: the pod is what puts the database on `localhost`,
   and a bridge topology needs `DATABASE_URL` pointed at a service
   name, a migration that runs once instead of in every replica, and a
   front. That is not a flag's worth of difference; it is a second
   file, and the seed's header says so.
3. **A second seed, `docker-compose.scaled.seed.yml`, baked by
   `wb.sh`.** Chosen. Its shape follows from §2.5 and §2.8:
   * **One alias, every address.** All replicas carry
     `networks.default.aliases: [app]`. Docker's embedded DNS answers
     `app` with one A record per replica — the Compose spec's "not
     guaranteed" resolution is, on the wire, the full set — which is
     the shape a Kubernetes headless Service and Fly's `.internal`
     give a query (§2.8). The alias is therefore what
     `DNS_CLUSTER_QUERY` must be *in this deployment*, and the
     `environment` block sets it to `app`, overriding the Kubernetes
     form the cartridge wrote in `.env`. The alternative — writing
     `app` into `.env` at install — would make the cartridge guess the
     deployment; the cartridge's default is the Kubernetes form, the
     override is the deployment's.
   * **The balancer, optional.** nginx round-robins over
     `app1..appN:4000` and stamps `X-Served-By` with the upstream
     address — the same address that is the node's name, so balancing
     can be seen without touching the project. `--no-balancer` removes
     it and its config; the per-replica host ports stay, so a specific
     node can always be addressed, which is what makes cross-node
     behaviour (a broadcast seen on two replicas) demonstrable.
   * **`--replicas N`**, default 4: the shape of the baked file, not a
     runtime scale, because `up --remove-orphans` has to know the
     service set to clear the previous shape.
   * **Migrate once.** `rel/overlays/bin/migrate` as a service the
     replicas wait for, so four boots do not race the same migration.
   * **Without the cartridge, the same file.** `bake_scaled_compose`
     drops only the `DNS_CLUSTER_QUERY:` line when the marker is absent
     (§2.5), so `DNSCluster` is `:ignore`d instead of polling for peers
     it can never reach and warning at every boot; the replicas run
     isolated behind the balancer, which `clustering_warning` says out
     loud. Replicas that do not know each other are a valid deployment
     — the README's *What clustering is, and is not, for* — and the
     deployment does not depend on the cartridge to exist.

   The one edge this cartridge adds to that picture is drawn in the
   README's figure.

### 3.5 One workspace, no cluster; one image, one cookie

Two facts the cartridge states rather than works around.

**A workspace cannot cluster with itself.** The pod gives every service
one address (§2.5); `DNSCluster` dials `basename@ip` for each address
the query returns (§2.2), through `:inet_res`, which sees exactly what
the DNS server answers (§2.6) — and in the workspace no name answers
with more than the one address the node already is. Note what this
rules out: the `getent hosts` single-address behaviour the README
records is the *libc's* selection and is irrelevant to `DNSCluster`,
which never asks the libc; the scaled deployment works precisely
because the resolver returns the whole record set. The alternative —
starting a second `app` container in the workspace compose for
demonstration — was rejected in §3.4.

**The cookie is baked.** `Mix.Release.make_cookie/2` writes a random
`releases/COOKIE` at assembly and the boot script reads it unless
`RELEASE_COOKIE` is set (§2.3). The scaled compose builds one image
(`build app1` builds them all, `wb.sh`'s comment) and runs it N times,
so every replica carries the same file and the cookies agree by
construction. Setting `:cookie` in `mix.exs`'s release config, or
`RELEASE_COOKIE` in `.env`, would let *different* images cluster — a
rolling deploy across versions — which the workbench's deployment does
not do; the cartridge leaves the cookie alone and the README says all
replicas must run the same image. That is also why `build --deploy
scaled` warns before building when the feature is absent: the named
node is decided by `env.sh` inside the image, and installing the
cartridge afterwards means building again.

### 3.6 Idempotency, and the mark

Three writes, three guards, one mark:

* `rel/vm.args.eex`, `rel/remote.vm.args.eex`, `rel/env.bat.eex`:
  `create_new_file` with `on_exists: :skip` — a hand-edited file is
  never replaced.
* `rel/env.sh.eex`: the block is appended only when the marker line
  `# Workbench clustering:` is absent. The marker is the header
  comment, not `export RELEASE_DISTRIBUTION=name`, because Mix's
  default template already contains that export *commented out*
  (§2.4): a substring test on the export would find the comment and
  skip a file that needs the block.
* `.env` / `.env.sample`: `WorkbenchIgniter.EnvFile.entry/4` appends only
  when the first `KEY=` of the body — `DNS_CLUSTER_QUERY` — is not in
  the file.

`installed?/1` is `marker_installed?(igniter, "rel/env.sh.eex", "# Workbench clustering:")`:
the same substring test the installer's guard makes, on the same file.
Two other marks were possible. The presence of `rel/env.sh.eex` — no:
the opinionated line's `mix release.init` leaves one in every project
(§2.7), and the cartridge is not in them. `DNS_CLUSTER_QUERY` in
`.env` — no: the scaled compose overrides it and would have worked
without it, and a developer can declare it by hand; what decides
whether the *image* boots distributed is the block in the boot script.
That is why `wb.sh`'s `clustering_installed` greps for the identical
string: the catalog, the installer and the deployment read one mark.

Re-running is asserted as a no-op by the test suite (`assert_unchanged`
after a second `compose_task`).

## 5. Limitations and open questions

* **The README's reasons, twice imprecise.** "POSIX `sh` only: the
  production runner image has no bash" — the image has bash; the
  constraint is that the release script sourcing the file is `sh`
  (§3.2). "The other three `mix release.init` templates, which have to
  exist alongside `env.sh.eex`" — they do not have to (§2.3); the
  reason is the vanilla line's division of labour (§3.3). Both are
  wording; the mechanism is right.
* **The opinionated line's README template** still documents
  `RELEASE_DISTRIBUTION`, `RELEASE_NODE` and `DNS_CLUSTER_QUERY` as
  project variables (§2.7) although its `.env` template no longer
  declares them and only this cartridge sets them. Either the table
  loses the rows or points at the cartridge.
* **One address per container.** `hostname -i` on a container attached
  to two user-defined networks returns two addresses; the block keeps
  the first, and which one is first is Docker's ordering, not a
  choice. A deployment where the cluster network is not the first
  should set `RELEASE_NODE` itself, which the guard honours.
* **`DNSCluster` is silent by design** (`log: false`, empty answer on
  error, §2.2). A misspelt `--dns-query` produces a release that boots,
  names itself correctly and never finds a peer, with nothing in the
  log. The cartridge could set `log: :info` — but the child is
  `phx.new`'s line in `application.ex`, and the cartridge's rule is to
  touch no Elixir. Open.
* **The cookie in `releases/COOKIE`** ties clustering to one image
  (§3.5). Rolling deploys across two release builds need `:cookie` in
  the release config or `RELEASE_COOKIE` in the environment; neither
  is set up, and `.env.sample` has no line for it.
* **`RELEASE_DISTRIBUTION=name` is unconditional** even when
  `DNS_CLUSTER_QUERY` is absent (the scaled compose without the
  variable, or a `prod` run of the workspace compose): the release then
  boots as a long-named node with distribution listening and nobody to
  talk to. Harmless, and `epmd` runs regardless; whether the block
  should test for the query first is open.
* **The scaled deployment over a dev deployment's database.** The two
  share one compose project, so `up --deploy scaled --remove-orphans`
  *recreates* the dev `database` container as the scaled one — and
  Compose carries the old container's anonymous volume over. Postgres
  only honours `POSTGRES_DB` when it initialises an empty data
  directory, so `lorem_ipsum_8_prod` is never created, `migrate` exits
  1 with `database "lorem_ipsum_8_prod" does not exist`, and the
  replicas, which `depends_on` it, never start (§4.1, first attempt).
  A workspace whose dev deployment has run needs `down` with its
  volumes — or a `createdb` — before its first scaled deployment; the
  seed could also give the scaled database a volume of its own. Open.
  *Settled 2026-09-05*, the other way round: the dev/prod seed declares
  the same `POSTGRES_DB`, so whichever deployment initialises the
  volume creates `APP_prod`, and the prod compose gained the one-shot
  `migrate` too.
