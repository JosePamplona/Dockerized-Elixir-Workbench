# Cartridge: specdd

SpecDD — spec-driven development with `.sdd` files beside the code — on
a stock `phx.new` project. **Pending**: the design is settled and the
files it plants are written; the installer is not.

* **Task**: `mix workbench.install.specdd` (does not exist yet)
* **Inserted by**: `wb.sh add specdd [--root NAME]` (once done); no
  collection picks it.
* **Requires**: nothing. Works on an API-only project too.

## Description

`phx.new` already writes an `AGENTS.md`: how Elixir and Phoenix are
written here. What it does not say is what an agent may change, what
must keep holding and where it must stop — that goes into every prompt
and is lost with it. [SpecDD](https://specdd.ai) puts it in the
repository: small `.sdd` files next to the code, a bootstrap the agent
reads first, and a resolution rule (walk up from the target to the
root, read the specs on the way, edit only within the nearest one's
authority).

This cartridge writes what `specdd init` writes — at a release pinned
in the cartridge, without touching the network — and then what `init`
cannot know: a `bootstrap.project.md` that says how this is an
Elixir/Phoenix project, and three starting specs for the project, `lib/`
and `test/`. The Phoenix usage rules stay where phx.new put them; the
SpecDD pointer goes on top of them.

## What it installs

```text
my_app/
├── AGENTS.md                  ← the SpecDD pointer prepended, phx.new's rules kept below
├── CLAUDE.md                  ← "Follow instructions in the AGENTS.md file." (created if absent)
├── my_app.sdd                 ← root spec, named after the content root (--root)
├── .specdd/
│   ├── bootstrap.md           ← SpecDD 1.5, verbatim (the framework's rules; `specdd update` owns it)
│   ├── bootstrap.project.md   ← this project's rules: Elixir/Phoenix, commands, layout, spec placement
│   ├── bootstrap.local.md     ← the operator's own; git-ignored
│   └── .gitignore             ← `bootstrap.local.md`
├── lib/
│   └── lib.sdd                ← the domain / web boundary
└── test/
    └── test.sdd               ← the suite mirrors lib/
```

* **`AGENTS.md`** — the three-line pointer of the SpecDD distribution
  ("Before working on this project, read `.specdd/bootstrap.md`…"),
  prepended between `<!-- specdd-start -->` / `<!-- specdd-end -->`
  markers, phx.new's own text untouched below. A project generated with
  `--no-agents-md` gets the pointer alone.
* **`CLAUDE.md`** — created with the distribution's one line when the
  project has none; an existing one is left alone with a notice.
* **`.specdd/bootstrap.md`** — byte for byte the file of SpecDD release
  1.5 (`Version: 1.5` in its front matter, which is what
  `specdd check-update` and `specdd update` read).
* **`.specdd/bootstrap.project.md`** — rendered for the project: the
  content root and the root spec's name; that phx.new's usage rules in
  `AGENTS.md` stay in force (SpecDD says *what* may change, they say
  *how* it is written); `mix precommit` as the verification; the
  `lib/my_app` / `lib/my_app_web` / `test/` layout; how a spec is placed
  in Elixir, where a context module and its directory share a basename
  (`accounts.ex` beside `accounts/`: one `accounts.sdd` is both the
  module's same-basename spec and the directory's parent-held spec);
  `@MyApp.Accounts.get_user!/1` as the symbol form; generators; no
  specs under `deps/`, `_build/`, `priv/static/`.
* **`.specdd/bootstrap.local.md`** and **`.specdd/.gitignore`** — as
  the CLI writes them.
* **`my_app.sdd`** — `Platform: Elixir/Phoenix`, the top-level
  `Structure` (`./lib`, `./test`, `./config`, `./priv`, `./assets` when
  the project has it, `./mix.exs`, `./AGENTS.md`), `Owns` for the
  project files no child spec can (`mix.exs`, `config/`,
  `.formatter.exs`), three `Must` (`mix precommit` passes; secrets come
  from the environment through `config/runtime.exs`; tests mirror
  `lib/`) and one open task: replace the generic `Purpose` with what
  the application is for. Rendered for an app named `probe`:

  ```sdd
  Spec: Probe

  Platform: Elixir/Phoenix

  Purpose:
    A Phoenix web application, generated by `mix phx.new` and grown one
      workbench cartridge at a time.

  Structure:
    ./lib: Application code, the domain and its web interface
    ./test: ExUnit suite, mirroring ./lib
    ./config: Compile-time and runtime configuration, per environment
    ./priv: Migrations, static files and gettext catalogs
    ./assets: Front-end sources, built into ./priv/static
    ./mix.exs: Project definition, dependencies and aliases
    ./AGENTS.md: How Elixir and Phoenix are written here, kept by phx.new

  Owns:
    ./mix.exs
    ./config
    ./.formatter.exs

  Must:
    `mix precommit` passes before work is reported complete.
    Secrets reach the application through the environment, read in ./config/runtime.exs.
    Tests live in ./test and mirror the path of what they test.

  Tasks:
    [ ] Replace Purpose with what Probe exists to provide.
  ```

* **`lib/lib.sdd`** — the one boundary Phoenix has and agents cross
  most: the domain in `lib/my_app` knows nothing of HTTP, the web layer
  in `lib/my_app_web` reaches it through context functions; `Must not`
  for the two plausible mistakes (domain code reading a `@Plug.Conn`,
  business rules in a controller or LiveView).
* **`test/test.sdd`** — `Platform: ExUnit`; the suite mirrors `lib/`
  path for path, a spec's `Scenario` has a test before its task is
  marked done, `mix test` runs it; `Can read: ../lib`.

Nothing is added to `mix.exs`: SpecDD is files, not a dependency.

## Options

* `--root NAME` — the root spec's name, `NAME.sdd`. Default: the app
  name (`my_app`). SpecDD names the root spec after the **directory** the
  project lives in, and its tools only find it under that name — the
  app name is what `phx.new` calls that directory and what a clone is
  most likely called, but the workbench's own workspace directory
  (`WORKSPACE_PATH`, e.g. `_workspaces/test_50`) is not it. Pass the
  host directory's basename when they differ; `bootstrap.project.md`
  names the spec either way, so an agent reading the bootstrap chain
  finds it.

## The mark

`.specdd/bootstrap.md` — the same file the CLI keys on: `specdd init`
refuses when it exists, `specdd update` requires it and reads its
`Version`. So the installer, `mix workbench.status` and the CLI can never
disagree on whether SpecDD is in. A second run is a no-op with a notice
(`rerun: :noop`). `state/1` reads back `%{version: "1.5", root:
"my_app"}` off the front matter and the root spec found, so the console
shows the SpecDD release the project actually carries — after a
`specdd update` too.

## Afterwards

The SpecDD Agent Skills (fifteen skills — author, plan, do, review,
trace… — for agents that read the Agent Skills standard) are not
planted: they are a release of their own, deployed by the CLI into
`.agents/skills/`. The catalog's `afterwards` says so:

```bash
docker run --rm -v "$PWD:/workspace" ghcr.io/specdd/cli:latest agentskills deploy
```

## Updating SpecDD, and running its tools

The framework's rules are one file, `.specdd/bootstrap.md`, and the CLI
overwrites **only that file** on update — everything else this cartridge
wrote survives. No local install is needed; the CLI's image runs from
the project directory. Mount it under the root spec's name, or
`resolve` and `inspect` will not see the root spec (they look for
`<directory>.sdd`):

```bash
docker run --rm -v "$PWD:/my_app" -w /my_app ghcr.io/specdd/cli:latest check-update
docker run --rm -v "$PWD:/my_app" -w /my_app ghcr.io/specdd/cli:latest update
docker run --rm -v "$PWD:/my_app" -w /my_app ghcr.io/specdd/cli:latest lint
docker run --rm -v "$PWD:/my_app" -w /my_app ghcr.io/specdd/cli:latest resolve lib/my_app/accounts.ex
```

## Contents

| File | Role |
| --- | --- |
| `specdd.ex` | Manifest only (`pending?/0` returns `true`); says the mark and `afterwards` |
| `NEED.md` | The developer's need |
| `DESIGN.md` | Why it is shaped like this: what `init` writes, what `update` touches, the root-name rule, verified with the CLI |
| `priv/features/specdd/assets/bootstrap.md` | SpecDD 1.5's bootstrap, verbatim (`embed_assets`) |
| `priv/features/specdd/assets/{AGENTS,CLAUDE,bootstrap.local}.md` | The distribution's other three files, verbatim |
| `priv/features/specdd/templates/root.sdd.eex` | The root spec (`@module`, `@assets?`; its first line concatenates the newline EEx's `trim` would eat) |
| `priv/features/specdd/templates/lib.sdd.eex`, `test.sdd.eex` | The two starting specs (`@app`, `@module`) |
| `priv/features/specdd/templates/bootstrap.project.md.eex` | The project's rules (`@root`, `@app`, `@module`) |

`.specdd/.gitignore` is one line and is written from the installer, not
an asset: `Path.wildcard` behind `embed_assets` skips dot-files.

Cartridge test: none until the installer exists. What it should cover:
